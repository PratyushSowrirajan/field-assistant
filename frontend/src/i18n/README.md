# Multilingual support (English / Hindi / Marathi)

## Why this was rebuilt instead of ported

Investigated the old prototype (`PratyushSowrirajan/Krishi-Rakshak`) before
building this. Two problems with reusing it directly:

1. **It didn't ship Marathi.** Its three languages were English/Hindi/Punjabi
   — there is no Marathi content anywhere in that repo. If you remembered
   Marathi being there, that's not what actually shipped.
2. **The switching mechanism itself was broken-ish.** It called
   `window.location.reload()` on every language change — twice, from two
   different components that didn't agree with each other (one wrote to
   `localStorage` directly and bypassed the other's state). A real SPA
   language switch shouldn't reload the page at all.

What *was* worth keeping: the overall shape (a `t("key")` function reading
from per-language dictionaries) was reasonable — just not the reload-based
implementation. So this is a clean rebuild using `react-i18next` (a
standard, well-tested library) with fresh English/Hindi/Marathi content,
not a port of the old code.

## How it works

- `src/i18n/index.ts` — `react-i18next` setup. Detects the saved language
  from `localStorage` (key: `sfa_lang`), falls back to the browser language,
  then to English.
- `src/i18n/locales/{en,hi,mr}.ts` — one flat-ish nested dictionary per
  language, grouped by page/feature (`nav.*`, `home.*`, `fieldDetail.*`, etc).
- `src/components/LanguageSwitcher.tsx` — the dropdown, used in the main
  `Layout` header and on the login/register screens.
- Switching languages just calls `i18n.changeLanguage()` — no reload. Every
  component using the `useTranslation()` hook re-renders automatically.

## Scope — what is and isn't translated

Static UI chrome (navigation, buttons, headings, form labels, empty states,
status/severity words) is translated across every page. **Farmer-facing
content generated by the backend or the AI models is not** — alert messages,
detection class names in free text, and the Assistant's LLM answers stay in
English, because they're dynamic content generated server-side, not strings
this dictionary can own. Translating those would mean localizing the
backend's text generation itself, which is a separate, larger piece of work
than "translate the app's screens."

A small fixed exception: the Leaf Check model only has 7 possible class
labels (`Healthy Leaf`, `Insect Pest Disease`, etc.) and a small set of
risk/status enum values (`LOW`/`MODERATE`/`HIGH`/...) used all over the app —
these *are* translated (`leafCheck.classes.*`, `status.*`, `health.*` in the
locale files) since they're a small, known, fixed vocabulary rather than
open-ended generated text.

## Adding a new string

Add the key to all three locale files (`en.ts`, `hi.ts`, `mr.ts`) with the
same key path, then use `t("your.key")` in the component. TypeScript won't
catch a missing translation in one language — there's no automated check for
key-set parity across the three files, so double-check by hand when adding
new keys.
